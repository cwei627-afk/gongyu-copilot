# Stage F 实施方案

依据本轮两份 Stage F / F-Data 指令，2026-10-03。此文件记录实施方案，不代表验收已经通过。

1. 冻结原 A/B/C/D/E1 源码、测试、Schema、DSL、正式三应用和原知识库；保存读前文件及线上图指纹。通过兼容模块增加能力，不把确定性分析改成 Agent。
2. `frontend/` 使用 React + TypeScript + Vite，无 UI 框架；构建后由独立 FastAPI BFF 静态托管，浏览器只访问同源 Gateway。密钥只在服务端，正常界面不显示内部阶段或 JSON。
3. `app/copilot/` 增加安全门禁、闭合意图契约、显式实体/时间解析、Published API 调用和确定性展示映射。高置信规则直接路由，歧义澄清；分类对象不具有业务回答权限。生产分析始终调用原 C，明确对象查询调用原 D，原已评审知识问题可继续调用 E1。
4. 有界列表查询由代码调用新增只读 Mock API，不增加原 D 的工具权限。默认 10、最多 20 条，参数化 SQL；查询历史记录明确展示日期，不将历史异常标记当成当前工艺结论。少量追问仅携带服务端签发的短期对象引用，不保存模型记忆或复制业务数据库。
5. 固定 seed + 显式 as-of 生成 400 炉次、100 订单、200 批次，覆盖 50 天、2 炉号、10 虚构钢种。独立 `FDEMO-*` 命名和扩展详情表；同一命名 run 幂等，旧 fixture 不更新。额外生产字段不进入原严格业务 Schema。
6. 生成 30 份原创虚构受控正文及历史/未来/撤销版本；公开资料只做有登记、可追溯的简短改述。扩容内部资料和公开参考建立两个独立 Qwen 索引，原 5 文档索引不变。
7. 扩容知识采用 E1 兼容 Workflow：复用冻结 Stage A hit 验证和 Stage B JSON/schema/生成后验原则，人工评审问题与原文支持表随资料扩充。不宣称任意自然语言蕴含判断。新索引使用独立应用，原 E1 保留回归；这是知识能力的兼容扩展，不是新增 Agent。
8. UI 仅显示真实已验证结果派生的处理阶段；等待期间只显示“正在处理请求”。来源明确区分企业规程、公开参考和 MES/ERP/WMS；技术详情仅白名单字段，默认折叠，不包含原始模型文本或 secret。
9. 验证：新 Router/Presenter/Gateway/数据/来源测试 → 前端构建 → 真实索引与发布调用 → 浏览器桌面/移动端 → 全 pytest、Compose、原三应用发布回归、Citation probe、凭证扫描；失败保留并修复后重跑。

边界：只读 PoC、人工确认，无生产认证/设备控制/开放式数据库查询；原应用和资料始终留作可复核的冻结基线。
